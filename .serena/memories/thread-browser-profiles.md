# Conversation browser profiles

`server/thread-browser-profiles.ts` resolves direct tasks, group tasks and single-threaded DM records through one conversation adapter. It stores requested and last verified mounted choice IDs, with per-bot maps for shared group/DM conversations. It never stores capabilities or sessions. Null means own browser; absence inherits the bot default.

`server/index.ts` mints capabilities frozen to browserProfileId/browserSession/thread generation. Native browser_profiles_list and browser_profile_select run before browser runtime discovery, with active capability, tool scope and action authorization. Management does not dispatch browser RPC or claim/release control. Selection applies next turn and preserves bot defaults/current mount. activation() distinguishes an explicit conversation request from an inherited default: explicit availability/refusal failures abort mounting with a visible error, while legacy default chat behavior remains. Engine availability is metadata only, never a browser start. Ready means matching mounted binding, not Chrome/page load.

`server/browser-profile-usage.ts` is the canonical busy-profile owner lookup for config removal/engine changes and browser restart guards. It includes active direct/group bindings and preserves busy default-profile protections. Its selection refusal reads actual TurnResources ownership and human holds, without changing either. TurnOwner contains threadId/generation; resolve its bot through the current direct thread or group speaker.

`GET/PUT /api/bots/:id/browser-profile?threadId=...` shares a discriminated state contract: active mount, requested choice, viewer choice, ready/pending/reconnect/error. PUT remains owner/admin-only and rechecks visibility after reading input. Viewer routes and scoped signed-in sites resolve active mount, then last verified mounted choice, then bot default; pending requests never activate through viewing. Signed-in sites pass explicit conversation scope even outside Team and retain viewer audience visibility checks.

`useThreadBrowserProfile` keys display state by bot/thread and sequences GET/PUT responses. Navigation or a newer mount prevents stale selection responses overwriting current Screen state. Screen signed-in sites are separate from bot-default administration.

My Chrome is unsupported for new conversation selection. host/browser.ts browserSessionSpec attaches every My Chrome alias to the same configured CDP connection, while sessionFor gives logical profile/audience IDs. Those IDs do not prove physical profile or audience isolation. Selection rejects My Chrome explicitly; an existing explicit request later changed to My Chrome fails activation rather than falling back. Existing bot-default/admin My Chrome remains unchanged.

Focused mounted fixture is server/mounted-browser-profiles.test.ts, using launchRestartableServer and actual captured native MCP HTTP capabilities with no Chrome launch. It covers deferred next-turn selection, actual server restart persistence, own/guest, tools/list uniqueness, denied tools, active-profile config/restart protection, invalid/deleted/unavailable activation without fallback. Always send explicit threadId. Isolate the primary fake provider dump through its own instance environment so auxiliary conversations cannot overwrite captured capability evidence. Targeted server/store.test.ts covers actual TurnResources refusal plus direct/group/DM persistence/isolation. Screen hook/component and route checks are focused separately. Native Screen screenshot/page-action acceptance remains a separate mounted-tool gate.
